LLM Context大模型的上下文
模型在一次对话或一次生成中所能感知并利用的全部输入信息

  • 认识上下文长度限制带来的现实影响与常见处理策略

概念解释
大模型的"上下文"指模型在生成回复时所依赖的全部输入信息，通常包括系统提示词、用户此前的问题、历史对话、引用文档以及检索到的补充材料。它像是给模型的"临场记忆卡"：模型本身没有长期记忆，每轮回答都只能基于当前上下文窗口内的信息进行推理。因此，上下文里放了什么，模型就"看到""想到"什么，直接影响输出质量。
上下文窗口（Context Window）
模型一次能处理的 Token 数量上限。它规定了输入（系统提示+历史+用户请求+文档）与输出之和可占用的最大空间，是使用模型时需要时刻关注的计算边界。
Token 与分词
模型按 Token 读取文本，一个 Token 常对应一个或几个字符、单词片段。Token 数量决定上下文占用量，也直接关联计费与性能。
注意力机制
模型通过注意力权重权衡上下文各部分与当前生成任务的相关性，越相关的信息对输出影响越大。这也是"提供合适上下文"能显著提升效果的原因。
上下文管理
当内容超出窗口时，需要通过摘要、截断、检索（RAG）或分段处理等方式管理上下文，确保关键信息保留、尽量不丢失语义。

应用场景
长文档问答助手
知识库场景下，用户上传一篇数百页的研究报告，希望提问其中的细节。由于文档远超上下文窗口上限，系统将其切片并做向量化检索（RAG），每次只把与问题最相关的一小段放入上下文窗口，引导模型基于这些片段回答。
该场景体现了对"上下文"管理的典型工程处理：一方面通过检索把最相关信息塞进有限窗口，另一方面通过系统提示约束模型只能依据给定片段回答、避免幻觉。整个系统的效果取决于能否在"有限的上下文"里放入"正确的信息"。
概念辨析
上下文和无状态模型之间是什么关系？
大模型本身是无状态的——它不记住之前对话，每次调用都重新计算。所谓"多轮对话记忆"，实际是把历史对话一起塞进上下文窗口当作输入。因此上下文越大越能"记住"更多，但也受窗口硬上限约束。
上下文越长就一定越好吗？
不一定。窗口越长，成本越高、延迟越大，且注意力分散可能降低对关键信息的聚焦。很多场景下用小而精的上下文往往比塞满一屏更有效，这也是检索增强（RAG）的价值所在。
自测检验
为什么说大模型"没有长期记忆"，但又能进行多轮对话？
因为模型每次推理都是无状态的，多轮对话只是把历史消息显式拼进上下文窗口一起送入模型。一旦某轮对话累积超过窗口上限，最古老的内容会被截断或丢弃，"记忆"也随之丢失。
当一次请求的内容超过上下文窗口时，有哪些常见解决方案？
常见方案有三种：把历史做摘要压缩；把长文档切分后只检索相关片段（RAG）；或者对输入做截断、仅保留最关键的指令部分。具体选哪种取决于保留信息完整性与可用窗口之间的权衡。
